# 0.22.0.dev20: explicit persistent wakes and recurring schedules

Spec #610; tickets #611–#616. Source delivery, not working-host deployment.

- New native agent registrations require an explicit session mode. Recurring
  schedules require explicit cadence, mode, end, missed-run/overlap policies and
  delivery windows. Existing legacy records and the older operator CLI policy
  interface retain their behavior.
- Wake owns interval and clock recurrence, original per-occurrence identities and
  UTC anchors. Clock schedules declare timezone and DST choices.
- Continuing modes recover scheduling after restart. Session-only wakes cancel
  on verified recipient process or pane loss; detach alone is not closure.
- Background uses the exact live TUI or starts the exact saved conversation via
  app-server turn/start. Live restoration reuses current approved profiles and
  existing durable resume/terminal lifecycle owners. Unknown identity holds.
- CLI/MCP support inspection, revisions and cancellation; running/uncertain work
  is not replayed or silently interrupted. Failed restoration enters attention.

Compatibility: mode-aware schema8 records include a frozen `session_mode` policy
extension. Older closed-shape policy readers hold these records instead of
executing legacy startup semantics. A mode registration reports
`requires_worker_capabilities: ["wake_session_modes_v1"]`; active recurring
schedules additionally require `recurring_schedules_v1` in a compatible live
monitor heartbeat. Merely advertising schema8 is insufficient. Legacy policy
records without the extension are unchanged. No existing wake is rewritten.

See [operating guide](../../agents/persistent-wakes.md) for explicit request shapes
and restoration prerequisites. Installed source capability, monitor readiness,
accepted execution and production/provider acceptance remain separate outcomes.
