# Codex Wake 0.20.0 candidate — Codex/Grok wakes and exchanges

Status: release preparation, not published or installed into production.
Plan0172's implementation is merged through PR306; PR307 records integration
and fixture corrections. Qualification of the newly numbered 0.20.0 package is
a separate release gate. The live behavior evidence below came from an isolated,
unreleased 0.19.1 acceptance build; it is not an installation receipt for 0.20.0.

## What changes

A shared runtime adapter separates recipient resolution, readiness, submission
and reconciliation from durable scheduling. Existing Codex native identities,
actor grants and record meanings remain intact. Grok gains durable wakes to an
exact managed open TUI and scoped Codex → Grok / Grok → Codex mailbox requests,
explicit work claims and correlated replies.

The qualified Grok route is Grok 1.0.40 (eb1a2256660d stable), minimal UI with the
Grok 4.7/high footer, an exact private tmux pane, and a pinned executable, process
generation and session binding. The operator must approve terminal input. A
native-preferred profile may use terminal fallback only with explicit host
approval and definite native-unavailable evidence before submission I/O.
A changed version, binding or composer refuses input rather than guessing.

Terminal observation proves delivery only. Work still requires an independent
issued actor capability, exact managed caller context and a new acknowledgment
returning `claimed=true`. Host-bound Grok delegation is not native Grok caller
attestation. The agent-facing MCP catalog adds five Grok tools, bringing the
catalog to 32; operator binding enrollment remains outside model tool arguments.

## Evidence and limits

The accepted real-TUI sample used Codex 0.164.0 and Grok 1.0.40. Both directions
authenticated, claimed and returned correlated replies; each TUI showed two
completion responses. Four original synthetic prompt attempts completed in
33.623 seconds with a clean owned-runtime census. The isolated acceptance
package passed 1,455 local tests with zero failures/errors and one expected
opt-in systemd skip, plus 61 installed focused checks. Required Python 3.11/3.12
PR release gates subsequently passed. Original failed, stopped and uncertain
samples remain recorded; later successes do not erase them.

[Acceptance evidence](../verification/0172-2026-10-22-mr06-installed-acceptance.md)
and the [support/recovery guide](../multi-runtime-mailbox.md) define the exact
versions, methods and remaining gaps. Grok CLI tool children were exercised in
both real TUIs; a live Grok MCP-host model connection was not independently
qualified.

Wait is the default busy policy. Queue and interruption selections explicitly
refuse before effects; no dequeue-expiry or owned-turn interruption guarantee is
introduced. Native Grok caller attestation, Codex terminal fallback, saved Grok
resume/refresh/lifecycle, Grok usage accounting and strict cross-runtime resource
enforcement remain unqualified. Claude Code and other TUIs require their own
adapters and acceptance evidence.

## Reader compatibility and recovery

Grok durable intents use schema 7 and a separately versioned runtime target.
Existing Codex native intent writers retain schema 6 and their original meaning.
Older readers hold schema-7 records; current readers also hold unfamiliar runtime,
envelope, method or policy combinations. Every reader responsible for a root
must support its records. Quiesce incompatible resident readers before admitting
new runtime work; installing a new executable alone does not prove their upgrade.

On rollback, preserve original schema-7 records and restore a capable reader.
Do not downgrade targets, recreate intents or replace idempotency keys to make an
older scheduler process them. Cancellation, expiry, clock uncertainty and restart
retain the original intent and deadline. See the
[record contract](../wake-record-schema.md#runtime-intent-version-7-runtime-envelope-version-1).

Terminal repaint can lag Enter. The adapter observes the original marker within
its bounded observation window and original deadline, without a second paste.
Missing or ambiguous acceptance remains uncertain: inspect/reconcile that
original attempt and never resend it with a new key. A terminal receipt is not an
execution result or mailbox work claim. Keep anomalous clock checkpoints intact;
the acceptance run explicitly selected the existing network-first plain-NTP
policy on a new isolated bus, not authenticated UTC or a production-policy reset.

Publishing a release, changing the production tool prefix, upgrading resident
readers/services and granting live runtime access remain separate actions with
exact artifact and post-effect readback requirements.
