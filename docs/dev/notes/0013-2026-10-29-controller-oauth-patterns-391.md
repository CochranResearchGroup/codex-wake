## Decisions required before specification

These are proposed contract shapes inferred from the sources, not existing Wake APIs or operator selections.

1. **Issuer/resource authority:** choose Wake's canonical HTTPS issuer and resource(s), discovery/challenge locations and TLS/proxy ownership. Graphiti, Mail Receipts and OpenSign pin tokens to `issuer + /mcp`; OpenSign also accepts that token at one direct API. Decide whether Wake API and MCP are one protected resource or separate audiences; do not accidentally accept arbitrary provider, ID or other-service tokens. SSH must map its authenticated identity into the same authorization policy without treating an SSH tunnel as OAuth authorization.
2. **Principal and delegation:** use a verifier returning `AuthenticatedPrincipal(subject, client_id, grant_id, issuer, resource, scopes, target_grants, expires_at, authority_epoch)` rather than Graphiti/OpenSign's boolean. Their token store retains client identity, but `verifyAccess()` does not expose it downstream. DCR client names/IDs identify registrations, not trustworthy people or Bots authority. Choose owner-only versus multiple operators/service identities, Bots enrollment/consent and whether explicit on-behalf-of delegation is supported. The inspected flows do not establish a reusable general token-exchange/delegation protocol; do not infer one from refresh grants.
3. **Operation/target grants:** define `authorize(principal, operation, target_identity)` independently of adapter. Mail Receipts supplies the useful current-policy intersection pattern; LitScout supplies account/actor binding. Select named Wake capabilities and target constraints before adopting an unrestricted owner scope. Candidate capability divisions are observation, attach/input and recovery/administration; these names are proposals, not accepted vocabulary. Health observation cannot confer input or recovery authority.
4. **Transport and session ownership:** distinguish OAuth grant, MCP connection/session, SSH connection, Wake daemon connection and exact TUI conversation/process generation. [Mail Receipts sessions](https://github.com/ecochran76/mail-receipts/blob/cdfa856c13229582104a49d4f3e1dcf89d444f70/src/mail_receipts/client/oauth.py#L741-L838) bind session ID to bearer digest, cap/expire sessions and revalidate under the session lock; token rotation therefore cannot silently adopt an old transport session. OpenSign is stateless; Graphiti forwards to an upstream transport. Choose reconnect/rotation/cancellation/duplicate-attachment semantics explicitly. Neither transport model supplies Wake TUI ownership by itself.
5. **Revocation and restoration:** select access lifetime, refresh rotation/replay response, per-client/grant revocation, global epoch invalidation, restored-store behavior and in-flight cancellation. Revalidate policy for each privileged action; deleting a browser session or moving a database is not a complete policy. LitScout's inspected metadata does not advertise an OAuth revocation endpoint; its hosted-session revocation and refresh rotation must not be described as the same family-revocation interface without further evidence. No live revocation behavior was tested.
6. **Provider/process boundary:** caller OAuth authenticates access to Wake; Codex/provider account credentials remain private to their owning runtime and are never forwarded to a controller client. Graphiti's credential-stripping fixed-loopback edge and OpenSign's separate business-admission gate are useful patterns. Choose how local daemon IPC trusts a verified edge, which callers can reach direct listeners, how audit identity survives forwarding, and how a closed business gate affects metadata/login/health. OAuth alone does not authorize changing an installed account, package or live process.

## Initial Bots acceptance input

[#390](https://github.com/CochranResearchGroup/codex-wake/issues/390) requires an exact controlling TUI main-loop challenge acknowledgment, with conversation/namespace/account/backend/channel/process-birth/boot/connection-generation binding and finite deadlines. An authenticated reply from the OAuth edge or a healthy background worker cannot manufacture this positive result. Timeouts, mismatches and unsupported capability remain unknown; observation does not grant recovery authority. It must preserve drafts/private input/history/queues and avoid model turns, notices, resume or other application effects.

Therefore initial direct API, OAuth MCP and SSH adapters must share the same principal/target/capability checks and health evidence contract. Carry Bots compatibility into #388/#389 with explicit delivery or deferral; source research cannot qualify the disposable end-to-end Wake-to-Bots boundary, native build or live fleet compatibility. Do not hand Bots an all-powerful owner grant solely because the simplest source examples do so.
